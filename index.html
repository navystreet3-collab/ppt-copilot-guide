02

各ファイルの役割

1ファイル1責務を基本に、Copilotが変更範囲を判断しやすい境界を作ります。

README.md

セットアップ、実行方法、設計方針、成果物の場所を記載。

requirements.txt

python-pptxを基本とし、明確に必要な依存だけを固定。

.gitignore

仮想環境、キャッシュ、生成した.pptxをGit対象外にする。

.github/copilot-instructions.md

設計の要点をGitHub Copilotへ常時適用する短いルール。

assets/

スライドで使用する画像・アイコンを格納。フォントファイルの同梱は前提にしない。

template/

背景、マスター、ロゴ、フッターなどを保持する生成の土台。色・書体・本文レイアウトの正本にはしない。

references/

見た目・情報設計を学ぶデザイン参考資料。今回の事実・数値・判断の情報源とは分離する。

design/reference_analysis.md

参考資料から確認した共通ルール、差異、確認できなかった制約を記録。

design/design_spec.md

設計仕様の正本。変更時は先に更新し、theme.pyとテストを同期。

tools/analyze_references.py

参考PPTXの色、フォントサイズ、座標、図形サイズを機械分析。

inputs/

今回の資料内容の情報源（Excel、PPTX、md、txt、PDF等）とslides JSONを置く。元資料は読み取り専用。

pptxgen/theme.py

色、書体、文字サイズ、間隔、semantic styleを一元管理。

pptxgen/geometry.py

Boxと12カラム論理Gridを扱い、themeの余白・gutterから主要領域の座標を計算。

pptxgen/components.py

指定領域へ統一された部品を描画し、低レベルAPIを隠蔽。

pptxgen/layouts/

座標と領域配置、layout固有の情報量上限を管理。

tests/test_generation.py

標準のunittestで生成、layout解決、validator結果を確認。

outputs/

生成PowerPointと、Evidence・Story・Slide Planなど今回作業の一時成果物を保存。ユーザー入力は置かない。

04

Copilotに渡す初期構築・更新プロンプト

新規構築にも既存基盤の差分アップグレードにも使える実践版です。既存フォルダやreferencesを保護しながら、会社テンプレートを「生成の土台」として扱う設計へ更新します。

copilot-foundation-prompt.txt
あなたは、python-pptxを使って高品質なPowerPoint資料を自動生成するための「PowerPoint生成基盤」を、現在のworkspace内に実際に構築するエンジニアです。

このプロンプトはGitHub CopilotのAgent mode、または同等に複数ファイルの作成・編集とターミナル実行が可能な自律実行環境で使うことを前提とします。
説明やコード例を回答するだけで終了せず、workspace内のファイルを作成・編集し、サンプルPowerPointの生成、検証、テスト、ドキュメント整備まで完了条件を満たすところまで進めてください。

目的は、Copilotが毎回スライドを自由描画するのではなく、決められたデザインシステム、再利用可能なcomponents、layout library、入力契約を使ってPowerPointを生成する状態を作ることです。

特に次の問題を構造的に防いでください。

- 背景色と文字色が同化する
- スライドごとにフォント、文字サイズ、余白がばらつく
- 図形の位置やサイズが不揃いになる
- テキストがはみ出す
- 1枚の情報量が過多になる
- 色、座標、書体がコード各所に分散する
- 同じ部品がlayoutごとに再実装される
- slides.jsonの構造がlayoutごとに場当たり的になる
- 「コンサル資料らしい」情報階層や視線誘導にならない

# 1. 実行前確認と進め方

現在VS Codeで開いているworkspace rootを、このPowerPoint生成基盤のproject rootとして扱ってください。
すでにppt-generator等のproject folderを開いている場合、その配下にさらにppt-generator/を作成してはいけません。
後述のフォルダツリーにある「ppt-generator/」は、現在のproject rootを意味します。

最初に現在のworkspaceを確認してください。

確認対象：
- Pythonの利用可否
- python-pptxの利用可否
- template/
- references/
- inputs/
- 既存のpptxgen/、design/、tests/、README.md
- .github/copilot-instructions.md
- .github/instructions/
- AGENTS.md
- その他既存のAI向けinstruction
- 既存ファイルを上書きすると影響があるか

既存実装がある場合は、全面破棄せず、今回のarchitectureへ安全に統合してください。
すでにこのプロンプトの旧版を実行済みで、pptxgen/、design/、tests/、references/等が存在する場合は「新規構築」ではなく差分アップグレードとして扱ってください。
既存のフォルダ構成を理由なく作り直したり、references/内の資料を移動・改名・再配置したりしないでください。
既存のreference_analysis.mdがあり、referencesの内容が変わっていない場合は、必要な差分だけ確認し、全資料の再分析を強制しないでください。
既存のCopilot/Agent向けinstructionがある場合は、今回のPowerPointルールで全面置換せず、競合を確認して既存ルールを保持しながら統合してください。

## Existing Customization Protection

このprojectは、過去の基盤構築後にユーザーが独自のカスタマイズを追加している可能性があります。

既存実装とこのプロンプトの標準形との差異を、すべて「修正すべき逸脱」と判断してはいけません。
意図的な既存カスタマイズは、このプロンプトの標準形へ戻すことより優先して保持してください。

特に以下は、今回の要件との直接的な競合、再現可能な不具合、重大な品質問題がない限り維持してください。

- 独自layout
- 独自component
- theme / Design Token / Typography / spacingの調整値
- Data Contractの追加項目や互換拡張
- renderer / validator / geometryの独自拡張
- 独自の命名規則
- sample / testの追加ケース
- README / design_spec / copilot-instructionsへ追加されたルール
- その他、既存project内で利用されている意図的な実装

変更前に、今回影響を受けそうな既存差分・拡張を確認し、少なくとも内部的に次のどれで扱うか決めてから実装してください。

- PRESERVE：そのまま保持する
- EXTEND：既存カスタマイズを残したまま今回要件を追加する
- MODIFY：今回要件との直接競合または不具合解消のため最小限変更する

判断が曖昧で、今回の要件を満たすために変更する必要がない場合はPRESERVEを既定としてください。
標準形へ揃えるためだけのrename、再配置、API変更、値の戻し、refactorは禁止します。

MODIFYが必要な場合も、全面置換より既存カスタマイズへ今回要件を統合する方法を優先し、変更理由と影響範囲をdesign/design_spec.mdまたは最終報告へ記録してください。

このCustomization確認だけを理由に実行を停止してユーザーへ確認を求めないでください。
既存コード、design_spec、tests、README、使用箇所から意図を合理的に推定できる範囲では、PRESERVE優先で最後まで進めてください。

技術的に実行不能、または結果を大きく左右する重大な情報欠落がある場合だけ停止してください。
それ以外の軽微な不足や差異は、後述の優先順位に従って妥当な判断で進め、判断理由をdesign/design_spec.mdへ記録してください。

template/、references/、inputs/に既存のユーザーファイルがある場合、それらは読み取り専用として扱い、上書き、編集、移動、削除をしないでください。
inputs/slides.jsonが存在する場合は変更しないでください。存在しない場合は、初期動作確認用としてinputs/sample_slides.jsonを新規作成してよいものとします。
サンプル生成にはsample_slides.jsonを使用し、ユーザー入力データをテスト目的で書き換えないでください。
生成したPowerPointなどの成果物はoutputs/へ新しいファイル名で保存し、既存生成物も明示的な指示なく上書きしないでください。

# 2. 設計判断の優先順位

デザインや実装方針が競合する場合は、次の順に優先してください。

1. 今回ユーザーが明示した要件
2. 意図的な既存カスタマイズと、現在のprojectで有効に機能している既存仕様
3. このプロンプトが示す標準architecture / 標準値（既存仕様がない領域のdefault）
4. template/に含まれるブランド必須要素
5. 三菱電機公式referencesに共通して確認できるVisual Identity
6. デジタル庁デザインシステム（DADS）v2.17.1から採用するDesign System原則
7. コンサルティング資料としての一般的な情報設計原則

このプロンプト内の色、layout数、Token構成、命名等の標準値は、既存カスタマイズを標準形へ戻すための強制値ではありません。
既存仕様が今回要件を満たしている場合は維持し、不足部分だけを補ってください。

この順位で解決できる差異については確認を求めず進めてください。
templateとreferencesの差異、採用した判断、確認できなかった事項はdesign/reference_analysis.mdまたはdesign/design_spec.mdへ記録してください。

# 3. Architecture

PowerPoint生成基盤を次の責務に分離してください。

## theme.py
デザイン値の正本です。

管理対象：
- Primitive Color Token
- Semantic Color Token
- Surface Style
- Typography Token
- Spacing Token
- Border Token
- Corner Token
- slide margin
- grid gutter
- 最小フォントサイズ
- validatorで共有するデザイン基準値

スライド固有の絶対座標は持たせないでください。

## geometry.py
座標計算だけを担当します。

最低限：
- Box
- SlideGrid
- content_area()
- 12-column logical grid
- column spanからBoxを計算する処理

色、フォント、spacing値そのものをgeometry.pyへ重複定義しないでください。
marginやgutterの値はtheme.pyを参照してください。

## components.py
再利用可能な描画部品を担当します。

- layoutからBoxまたはx/y/w/hを受け取る
- themeを参照して描画する
- python-pptxの低レベルAPIを隠蔽する
- スライド全体の領域分割を判断しない

## layouts/
1枚のスライド全体の情報配置を担当します。

- geometryのGridとBoxを利用する
- componentsを組み合わせる
- layout固有の最大文字量、最大項目数、必須項目を管理する
- rawな色コード、フォント名、フォントサイズを持たない
- slides.jsonから座標を受け取らない

## renderer.py
入力とlayout実装の橋渡しを担当します。

- slides.jsonを読み込む
- layout_idを解決する
- LAYOUT_REGISTRYから対応layoutを呼ぶ
- layoutごとのdata contractを検証してから描画する
- 未知のlayout_idを拒否する

## slides.json
内容だけを持つ入力です。

許可：
- layout_id
- title
- message
- heading
- body
- bullets
- KPI
- chart data
- image path
- source
- layoutが定義した内容項目

禁止：
- x
- y
- width
- height
- font_size
- font_name
- text_color
- fill_color
- line_color
- その他の直接的なデザイン指定

## Content Planning Boundary

この生成基盤のrendererは、Excel分析エンジンや汎用ドキュメント分析エンジンにはしないでください。

実際の資料作成時は、inputs/に置かれたExcel、PPTX、md、txt、PDF等から必要な情報を読み取り、
Evidence → Story → Slide Plan → slides JSON
の順で内容を整理してからrendererへ渡します。

この内容設計workflowは06の資料生成プロンプトで実行します。
04の初期構築時に、source_reader.py、excel_analyzer.py、story_engine.py、reasoning_engine.py等の新しい巨大subsystemを作らないでください。

references/はVisual Identityや情報設計を学ぶデザイン参考資料です。
今回の資料で事実・数値・判断材料として使用するファイルはinputs/へ置き、references/と混同しないでください。

# 5. 技術・依存関係

- Pythonを使用する
- PowerPoint生成にはpython-pptxを使用する
- テストにはPython標準ライブラリのunittestを使用する
- pytestは導入しない
- python-pptx以外の追加依存は、標準ライブラリでは実現できない明確な必要性がある場合だけ追加する
- PyYAMLやPillowを初期前提として追加しない
- 入力形式は標準ライブラリで扱えるJSONを基本とする
- テストは python -m unittest discover -s tests で実行できるようにする
- PowerPoint上で後から個別編集できる状態を維持する
- スライドを画像化して貼り付ける方式にしない
- 入力資料や生成物を外部サービスへ送信しない

追加依存が必要になった場合は、理由と標準ライブラリで代替できない理由をREADME.mdへ記録してください。

# 6. デザイン設計の3層構造

デザインを次の3層として扱ってください。

## A. Visual Identity：三菱電機
担当：
- ブランドカラー
- ロゴ
- 企業資料としてのトーン
- templateのブランド必須要素
- 三菱電機公式referencesから確認できる視覚的特徴

基本は「白ベース＋ブランドレッド＋チャコール／グレー」です。

## B. Design System：DADS v2.17.1を参考
担当：
- Design Token
- Typography hierarchy
- modular spacing
- logical grid
- semantic color
- reusable component
- accessibility
- consistency

DADSのWeb UIをPowerPointへコピーすることが目的ではありません。
DADS固有の青系Visual Identityへ変更しないでください。

採用しないWeb固有要素：
- breakpoint
- responsive / liquid layout
- hover / focus / active
- DOM / HTML構造
- Webフォーム
- Webナビゲーション
- Web UIコンポーネントそのもの
- リフロー要件

## C. Information Design：コンサルティング資料
担当：
- 1スライド1メッセージ
- タイトル
- ページメッセージ
- メッセージを裏付ける図、表、数値、情報
- 情報階層
- 視線誘導
- 比較のしやすさ
- 図解
- KPI
- Before / After
- Process
- Matrix
- Chart + Insight

装飾よりも情報伝達を優先してください。
情報量超過時はフォント縮小よりスライド分割を優先してください。

# 7. Design Token

theme.pyでTokenを一元管理してください。

## Primitive Color
例：
- BRAND_RED
- GRAY_900
- GRAY_700
- GRAY_500
- GRAY_300
- GRAY_100
- WHITE

三菱電機の正式なtemplateまたはreferencesからより適切な値を確認できた場合は、そちらを優先してdesign_spec.mdへ記録してください。

基準値として以下を利用できます。

- BRAND_RED: #E60012
- PRIMARY_TEXT相当: #1A1A1A

実際に使うものだけ定義してください。

例：
- TEXT_PRIMARY
- TEXT_SECONDARY
- BORDER_DEFAULT
- BACKGROUND
- ACCENT
- POSITIVE
- CAUTION
- NEGATIVE
- DISABLED

ブランドレッドは主にACCENTとして扱ってください。

## Surface Style
背景色と文字色を安全な組み合わせとして定義してください。

最低限：
- WHITE_PANEL
- LIGHT_PANEL
- RED_ACCENT_PANEL
- DARK_PANEL

例：
- WHITE_PANEL：white background + dark text + light border
- LIGHT_PANEL：light gray background + dark text + light border
- RED_ACCENT_PANEL：brand red background + white text
- DARK_PANEL：dark gray background + white text

component側はstyle=WHITE_PANELのように利用し、背景色と文字色を別々に自由指定しない設計を基本としてください。

## Typography
用途ベースで少数のTokenを定義してください。

- TITLE
- MESSAGE
- HEADING
- BODY
- CAPTION
- NOTE
- KPI_VALUE

フォントウェイトはRegularとBoldを中心にしてください。
DADSのNoto Sans JP自体を必須にしません。
生成コンテンツのフォントはdesign_spec.md / theme.pyを正本とし、referencesと実行環境で利用可能なフォントを踏まえて日本語フォールバック候補をtheme.pyへ定義してください。
template内のフォント設定を、生成コンテンツのTypographyへ自動取り込みしないでください。template由来の固定要素に既存フォントが使われている場合は、その固定要素を変更せず保持してください。

フォントサイズはreferencesとPowerPoint上の可読性を基準に設計し、スライドごとに自由なサイズを作らないでください。

## Spacing
3〜5段階程度のモジュラースケールを定義してください。

例：
- SPACE_XS
- SPACE_SM
- SPACE_MD
- SPACE_LG
- SPACE_XL

DADSの8 CSS pxという値をPowerPointへ直接コピーしないでください。
PowerPointの固定キャンバス、文字サイズ、referencesをもとに適切な値へ変換してください。
template内の既存余白やplaceholder配置を、生成基盤のSpacing Tokenへ自動取り込みしないでください。

同じ意味の要素には同じspacingを適用してください。
関連が強い要素ほど近く、異なる情報グループほど大きく離してください。

# 8. Grid / Geometry

DADSの12カラムグリッドを「主要領域の論理Grid」として参考にしてください。

代表的な領域分割：
- 12
- 9 + 3
- 8 + 4
- 6 + 6
- 4 + 8
- 3 + 9
- 4 + 4 + 4
- 3 + 6 + 3

SlideGridはmarginとgutterをtheme.pyから受け取り、column spanからBoxを返せるようにしてください。
column番号は1〜12の1-basedとし、span(start_col, column_count)の形式にしてください。

例：
- main = grid.span(1, 8) は「1列目から8列分」
- side = grid.span(9, 4) は「9列目から4列分」

spanの第2引数をend columnとして解釈しないでください。

ただし、全shapeを12カラムへ強制的にsnapさせないでください。
Gridが拘束するのは主にスライドの主要領域です。
card内部のpadding、アイコン、矢印、装飾、component内部の細かな配置は、受け取ったBox内で相対配置して構いません。

geometry.pyを巨大なlayout engineにしないでください。

# 9. templateとreferences

## template

template/consulting_template.pptxが存在する場合は、「Design Systemの情報源」ではなく「生成先PowerPointの土台（rendering substrate）」として利用してください。

templateから原則として継承・保護するもの：
- slide size
- slide master / background
- logo
- footer
- legal text
- その他の明確な固定要素

templateから生成コンテンツのDesign Systemへ自動取り込みしないもの：
- theme color
- font / typography
- spacing
- card style
- content placeholderの座標
- 既存本文layout
- template内のサンプル本文デザイン

生成するshape、text、chartの色・Typography・Spacing・Grid・Surface Styleはdesign/design_spec.mdとtheme.pyを正本として明示的に適用してください。

templateに複数のslide layoutがある場合は、master/backgroundを維持でき、不要なplaceholderが最も少ないneutral / blank相当のlayoutをbase layoutとして1つ選び、その選択理由をdesign_spec.mdへ記録してください。
templateの既存2カラム等のcontent layoutとpptxgen/layouts/を二重管理しないでください。

templateの背景がmaster/layout由来か、特定の既存slide上に直接置かれたshape/image由来かをPreflightで確認してください。
master/layout由来なら通常の継承対象とします。
slide-levelの背景しか存在せず、安全に継承できない場合は、複雑なshape cloneやXML操作を新規実装して無理に再現せず、Template inheritance: LIMITED としてdesign_spec.mdとREADME.mdへ制約を記録してください。

design/design_spec.md内にTemplate Contractを設け、少なくとも次を記録してください。
- template path
- slide size
- selected base layout
- fixed elements
- reserved areas
- content safe area
- inherited elements
- Design Systemへ取り込まない要素
- background origin（master / layout / slide-level / unknown）

reserved areaは、logo、footer、legal text等の「生成コンテンツで覆ってはいけない固定要素」だけに限定してください。
背景色帯や装飾図形を機械的にreserved areaへ含めないでください。

Template Contractのためだけにtemplate_manager.py、template_parser.py、template_contract.py等の新しいsubsystemを作らないでください。既存のdesign_spec.md、theme.py、geometry.py、renderer.pyで必要最小限に実装してください。

templateの解析は初期構築時またはtemplateが変更された時だけ行い、通常の資料生成のたびに再解析しないでください。

templateが存在しない場合は白紙の16:9プレゼンテーションから生成してください。

会社テンプレートが.potxの場合は、そのファイルを自動変換・改変しようとせず、PowerPointで.pptxとして保存した作業用コピーをtemplate/へ置く必要があることを報告してください。

## references
references/はデザイン・情報設計を分析する見本です。生成ベースとして直接利用しません。
実際の資料内容の根拠となるExcel、PPTX、メモ、PDF等はinputs/で扱い、references/から事実を引く運用を基本にしないでください。

三菱電機公式資料を3〜6資料程度用意することを推奨します。
資料数より、要約、比較、プロセス、グラフなど異なる表現を代表できることを優先してください。

PDFの全ページを機械的に処理する必要はありません。
視覚分析は代表性の高いページを中心に、合計10〜20ページ程度を目安にしてください。

PDFを視覚入力として確認できる環境では、見た目、情報密度、視線誘導、余白、カード、表、グラフを分析してください。

PDFを視覚的に確認できない場合：
- 確認したと仮定しない
- テキスト抽出だけから色、余白、レイアウトを断定しない
- PPTXなど機械分析可能な資料があれば補完に使う
- 制約をreference_analysis.mdへ記録する
- templateと利用可能なreferences、既定のVisual Identity、DADS原則を使って構築自体は続行する

PPTXがある場合はtools/analyze_references.pyを使い、python-pptxで色、フォントサイズ、座標、図形サイズなどを機械分析してください。

参考資料の本文、図、写真、ロゴを転載せず、抽象化したデザインルールとlayout patternだけを利用してください。

# 15. Color / 三菱電機スタンダード

資料全体は「白ベース＋ブランドレッド＋チャコール／グレー」を基本としてください。

- 背景は原則白
- 白地を十分に残す
- ブランドレッドは重要箇所に限定
- 通常本文はdark gray / charcoal
- 補助領域はlight gray
- 赤を大面積背景として多用しない
- 赤だけで意味を区別しない
- 通常系列はgray、注目系列はbrand redを基本とする
- 技術資料、業務改善資料、DX資料に使えるフォーマルで信頼感のある印象を目指す

DADSのカラーへ置き換えないでください。

# 16. Accessibility

アクセシビリティをデザイン品質の一部として扱ってください。

基本方針：
- 文字と背景のコントラスト比は原則4.5:1以上を目安
- 重要な非テキスト要素は3:1以上を目安
- 色だけで意味を伝えない
- 極端に小さい文字で情報量超過を解決しない
- テキストoverflowを検出する
- 情報密度が高すぎる場合は分割を優先する

写真、gradient、透過shapeなど機械判定が難しいケースを無理にERROR判定しないでください。
確実に判定できるSemantic Styleを中心に自動検証し、判定が不確かなものはWARNINGまたは目視確認対象としてください。

# 17. validator.py

validatorはERRORとWARNINGを分けてください。

## ERRORの例
- slide外へのはみ出し
- 未知のlayout_id
- 必須項目不足
- slides.jsonに禁止design fieldがある
- 最小フォントサイズ違反
- 定義外colorの明らかな使用
- 確実に判定可能な背景と文字のcontrast不足
- 生成PPTXを再度開けない

## WARNINGの例
- titleが長い
- body量が多い
- 情報密度が高い
- object overlapの可能性
- contrastを機械判定できない
- layout上限に近い

意図的な重なり：
- 親containerと内部要素
- background shape
- arrow
- decoration
などを可能な範囲で除外してください。

WARNINGが残っているだけで生成失敗にしないでください。
完了条件はERROR=0です。

validatorを完璧なPowerPoint layout engineにしないでください。
まず生成品質を優先してください。

- 移動しない
- 改名しない

# ファイル形式ごとの読み取り方針

## Excel

Excelは「分析対象の生データ」ではなく、既に記載されている結果・数値・管理表・コメント等の情報源として扱ってください。

- 既存セルの値、ラベル、表、コメント、管理項目を読む
- 既に記載されている集計結果・分析結果は利用してよい
- ユーザーの明示指示がない限り、新しい集計、統計分析、ランキング、相関分析、予測を行わない
- raw dataから新しいKPIや傾向を作らない
- 管理表では行単位の文脈を保ったまま課題・状態・コメント・対応を読む
- formulaの表示値を取得できない場合は推測しない
- 数値は単位、期間、対象範囲を可能な限り一緒に保持する

## PowerPoint

PPTXは既存スライドの内容を情報源として扱ってください。

可能な範囲で、
- title
- body text
- table
- chart title / label / accessible value
- annotation
- speaker notes（利用可能な場合）
を確認してください。

レイアウトや色から事実を推測しないでください。
グラフの値を機械的に取得できない、または画像にしか存在しない場合は、読めたと仮定しないでください。

## Markdown / txt / メモ

見出しや段落の文脈を維持して読み取ってください。
箇条書きを独立した事実として切り離しすぎず、前後の見出しや条件を保持してください。

## PDF

テキストとして確認できる内容を使用してください。
画像・スキャン・図表にしか存在しない情報を確認できない場合は、その制約を記録してください。

# 実行を止める条件

停止するのは次の場合だけです。

- 指定された情報源を1つも利用できない
- 資料目的を満たすには、存在しない事実を作る必要がある
- 重大な情報矛盾があり、どちらを採用するかで資料の主要結論が逆転する

それ以外の不足・矛盾・読取制約は明示的に残し、事実として確認できる範囲で最後まで進めてください。

outputs/work/project_review/

既存フォルダを上書きしないでください。

# Step 1：Source Inspection

最初に、指定された情報源を確認してください。

evidence.mdの冒頭にSource Coverage表を作り、最低限次を記録してください。

- source file
- file type
- 読取可否
- 確認したsheet / slide / section / page等
- 今回の目的との関連性
- 読み取れなかった要素
- 除外した範囲と理由

大きな資料を無条件に全件精読するのではなく、sheet名、slide title、見出し、目次、表のheader等から関連範囲を特定してください。

ただし早い段階で絞り込みすぎないでください。
後述のEvidence Extraction後に、重要な見落としがないかSource Coverageをもう一度確認してください。

# Step 2：Evidence Extraction

まず「資料に使うか」を決める前に、今回の目的に関係しそうな情報を広めに抽出してください。

Evidenceは元資料から確認できる内容だけにしてください。

主なtype：
- FACT：確定事実・数値
- STATUS：現在状態・進捗
- ISSUE：課題・問題
- DECISION：決定済み事項・方針
- ACTION：予定・対応事項
- OPINION：担当者コメント・意見・仮説
- CONSTRAINT：制約・前提

各Evidenceに最低限次を持たせてください。

- Evidence ID（E01, E02...）
- type
- statement
- source file
- source location
- context / condition
- limitation（必要な場合）

例：

E07 [ISSUE]
営業担当が潜在ニーズを次の提案へどう使うか未整理
Source: inputs/meeting_notes.md
Location: 「営業レビュー」節
Context: PoC抽出後の営業活用について

OPINIONや仮説をFACTへ格上げしてはいけません。
資料中の「検討中」「予定」「可能性」等を「決定済み」と表現しないでください。

# Step 3：Evidence Coverage Review

Evidenceを抽出した後、各情報源をもう一度確認してください。

特に以下の取りこぼしを確認してください。

- 結論と逆方向の情報
- 未解決事項
- 条件・例外
- 重要なコメント
- 決定事項
- 次回アクション
- 表の末尾や別sheetにある補足
- 過去資料にある前提
- 主張を弱める情報

この段階では「作りたいストーリーに合わない」という理由だけでEvidenceを捨てないでください。

情報源間で内容が矛盾する場合はevidence.mdにCONFLICTとして記録してください。
ユーザーが優先資料を指定していない場合、明示的な日付・版数から新旧が判断できるときのみ新しい情報を優先してよいものとします。
判断できない場合は勝手に解消しないでください。

# Step 4：Analysis / Claim Design

ここから初めて、Evidenceをもとに「何が言えるか」を整理してください。

資料全体について、

- Main Question
- Main Answer / Main Message
- Supporting Point
- Implication
- Recommended Action（必要な場合）

を考えてください。

Main Questionは、資料の目的と対象読者から「この資料で答えるべき問い」として設定してください。

各Claimは次のいずれかとして区別してください。

- FACTUAL CLAIM：Evidenceに直接書かれている
- SYNTHESIS：複数Evidenceを統合した解釈
- RECOMMENDATION：Evidenceを踏まえた提案

各ClaimにはEvidence IDを紐付けてください。

SYNTHESISは、元資料に直接書かれている事実のように表現してはいけません。
RECOMMENDATIONは、既存の決定事項のように表現してはいけません。

相関や同時発生だけから因果関係を断定しないでください。
原因が資料に明記されていない場合は「要因の可能性」「確認が必要」等、Evidenceの強さに合う表現にしてください。

強い結論を支えるEvidenceが不足する場合は、無理に主張を作らず、
- 表現を弱める
- 状況確認のメッセージにする
- 未確認事項として示す
のいずれかで処理してください。

# Step 5：Story Design

outputs/work/.../story.mdに資料全体の論理構造を作成してください。

最低限：

- Purpose
- Audience
- Main Question
- Main Message
- Supporting Points
- Evidence IDs
- Implications
- Actions / Decisions
- Known Gaps / Conflicts

経営・管理職向け資料では原則として結論先行を優先してください。
ただし、経緯説明、プロセス説明、時系列レビュー等では内容に適した構造を選んでください。

ピラミッド構造は「主張と根拠を整理する道具」として使い、無理にMECEへ押し込まないでください。

「元資料の章順」「Excelの列順」「既存PPTのスライド順」をそのまま新しい資料のストーリーにしないでください。

# Step 6：Slide Plan

story.mdをもとにslide_plan.jsonを作成してください。

各slideに最低限：

- slide number
- purpose
- title
- message
- evidence_ids
- layout_id
- content outline
- source note

を持たせてください。

1スライド1メッセージを基本とします。

messageの必須条件：

- 単なるテーマではなく、そのスライドで伝える主張になっている
- 1文で意味が通る
- Evidenceで裏付けられる
- 「だから何か」が分かる
- 前後slideとの論理接続がある

次のようなmessageだけで終わらせないでください。

- 「売上の状況」
- 「課題について」
- 「分析結果」
- 「今後の方向性」
- 「施策概要」

強い主張を作れない場合は、Evidenceに忠実な事実・状態メッセージにしてください。

既存layoutで表現できる場合は新しいlayoutを追加しないでください。
内容が入らない場合は、まず情報整理またはslide分割を行い、rendererを変更して解決しないでください。

# Step 7：Critical Content Review

PowerPointを生成する前に、一度作成者の立場から離れ、「この資料の結論を疑うレビュー担当」としてstory.mdとslide_plan.jsonを批判的に確認してください。

最低限確認：

## Source Coverage
- 重要なsourceを見落としていないか
- 結論に不都合なEvidenceを除外していないか
- 条件・例外・未解決事項を落としていないか

## Claim / Evidence
- 各messageにEvidenceがあるか
- Evidenceより強い言い方になっていないか
- OPINIONをFACTとして扱っていないか
- RecommendationをDecisionとして扱っていないか
- 因果関係を飛躍していないか
- 数値・固有名詞・状態が元資料と一致しているか

## Logic
- Main MessageをSupporting Pointsが本当に支えているか
- 「AだからB」「BだからC」の間に論理の飛躍がないか
- 前後slideが単なる話題の羅列になっていないか
- 同じ主張を複数slideで繰り返していないか
- 重要な「So What」が欠けていないか

## Audience
- 対象読者が判断・行動するために必要な情報になっているか
- 詳細すぎる情報が主張を埋めていないか
- ActionがEvidenceと課題に接続しているか

Content Reviewの判定：

ERROR：
- Sourceにない事実・数値
- factual claimに根拠がない
- Evidenceとmessageが明確に矛盾
- unresolved conflictを無視して主要結論を断定
- Opinion / Recommendation / 未決事項を確定事実として表現

WARNING：
- messageが弱い・抽象的
- 論理接続が弱い
- 代替解釈があり得る
- Evidence Coverageに不安がある
- Actionが抽象的
- 重複slide
- 因果表現が強すぎる可能性

ERRORがあれば、元資料を変更せずstory / slide planを修正してください。
修正・再レビューは最大2回程度とし、無限に繰り返さないでください。

解消できない問題はKnown Gaps / Content Warningsとして残してください。

PowerPoint生成へ進む条件はContent ERROR = 0です。

# Step 8：slides JSON

Critical Content Review後のslide_plan.jsonを既存Data Contractへ変換し、今回用のslides JSONを新規作成してください。

既存のinputs/slides.jsonや他のユーザーinputを上書きしないでください。

既存慣例がなければ、
inputs/slides_【案件名】.json
のように新しいファイル名を使ってください。

slides JSONには内容だけを持たせてください。

含めてよいもの：
- layout_id
- title
- message
- heading
- body
- bullets
- KPI
- chart data
- insight
- source
- image path
- 既存Data Contractで許可された内容項目

Evidence IDをrendererのためだけに新しい必須fieldとして追加しないでください。
必要な出典は既存のsource field等へ、人間が確認できる簡潔な形で反映してください。

直接的なdesign fieldは追加しないでください。

# Step 9：PowerPoint Generation

既存renderer / layout / componentを使用してPowerPointを生成してください。

生成物は指定されたoutputs/配下へ新しいファイルとして保存してください。
既存生成物を明示的な指示なく上書きしないでください。

今回の内容が既存layoutへ入りにくい場合は、

1. message / contentの整理
2. slide分割
3. 既存layoutの別案

を優先してください。

1案件だけの内容都合で、共有component / layout / Data Contractを安易に変更しないでください。

共有基盤を変更するのは、再現可能な描画不具合があり、他の資料でも再利用価値がある場合だけです。
変更した場合は既存unittestを実行し、副作用を確認してください。

# Step 10：Structural / Visual QA

生成後は既存05の品質検証フローに従ってください。

最低限：

1. validator
2. python -m unittest discover -s tests
3. 生成PPTXの再オープン確認
4. 利用可能ならPowerPoint Native Render
5. 利用可能ならVisual QA

Visual QAが利用できない場合は、実施済みと偽装せず既存statusルールに従ってください。

Content QAとVisual QAを混同しないでください。

- 内容の問題 → evidence / story / slide plan / slides JSONを修正
- 描画の問題 → components / layouts / validator等を必要な範囲で修正

## 技術方針

- Python 3を使用する
- データの読込、整形、結合、集計にはpandasを使用してよい
- Excelのシート、セル、数式、表、書式、入力規則、条件付き書式、グラフの生成にはopenpyxlを使用する
- pandasで処理する必要がない単純なデータまで、無理にDataFrameへ変換しない
- pandas.ExcelWriterは必要な場合に使用してよいが、最終的な書式とExcel固有機能はopenpyxl側で整える
- テストにはpytestではなく標準ライブラリのunittestを使用する
- 必須の追加依存はpandasとopenpyxlを基本とし、それ以外は明確に必要な場合だけ追加する
- VBA、Power Query、外部データベース接続、ピボットテーブルは初期基盤には含めない
- 元の入力ファイル、参考資料、テンプレートを上書きしない
- 実データがないサンプルでは、架空データであることを明記する
- 実際の業務用ファイルでは、与えられていない数値や事実を作らない

## フォルダとファイルの役割

- inputs/：集計・加工対象となるCSVまたはExcel。元ファイルは変更しない
- references/：見た目や構成を分析する参考資料。生成元として直接使用しない
- templates/：書式やシート構成を実際に継承するExcel。原本は上書きしない
- outputs/：生成したExcel
- design/excel_design_spec.md：設計とデザイン仕様の正本
- theme.py：色、フォント、数値・日付の表示形式
- styles.py：セル、表、見出し、KPI、グラフへの共通書式適用
- data_pipeline.py：pandasによる読込、型変換、欠損確認、結合、集計
- profiles/：用途別のシート構成、列構成、領域配置
- validator.py：生成後の構造、数式、書式、入力規則の検査
- workbook_spec.json：生成タイプ、タイトル、入力ファイル、項目、KPIなどの内容指定

templateが存在する場合は、templateを生成の土台として優先してください。
referencesは構成、配色、表示形式を分析する目的だけで使用してください。
inputsとtemplatesの元ファイルは変更せず、生成物は必ずoutputs/へ保存してください。

## カラーテーマ：三菱電機スタンダード

PowerPoint生成基盤と同じ「白ベース＋ブランドレッド＋チャコール／グレー」にしてください。

theme.pyで次の色を一元管理してください。

- BRAND_RED: #E60012
- PRIMARY_TEXT: #1A1A1A
- SECONDARY_TEXT: #555555
- DARK_GRAY: #333333
- MID_GRAY: #6E6E6E
- BORDER_GRAY: #D9D9D9
- LIGHT_GRAY: #F2F2F2
- VERY_LIGHT_GRAY: #F7F7F7
- BACKGROUND: #FFFFFF

基本ルールは次のとおりです。

- シート背景と通常セルは白を基本とする
- ブランドレッドは重要KPI、警告、注目系列、重要見出しに限定する
- 通常の見出しと本文にはチャコールまたはダークグレーを使用する
- 補助領域、入力説明、集計カードにはライトグレーを使用する
- 赤を表全体や大面積の背景に使用しない
- 赤だけで状態を区別せず、文字、記号、位置、ラベルを併用する
- 派手な装飾より、入力しやすさ、読みやすさ、比較しやすさを優先する
- 日本語フォントはYu Gothicを第一候補とする
- templateに指定フォントや正式なブランドカラーがある場合はtemplateを優先し、採用値をdesign/excel_design_spec.mdへ記録する

色、フォント、書式、配置の責務を次のように分離してください。

- theme.py：色、フォント、数値・割合・金額・日付の表示形式
- styles.py：themeの値を使ってセル、表、見出し、KPI、グラフへ書式を適用
- profiles/：シート構成、列構成、各領域の配置
- workbook_spec.json：タイトル、項目、数値、入力ファイル、生成タイプ

workbook_spec.jsonに色コード、フォント名、セル座標を持たせないでください。

## 3種類の生成profile

### analysis

原則として次のシートを作成してください。

- Readme
- Raw_Data
- Calculation
- Summary
- Dashboard

pandasを使って元データの型、欠損、重複を確認し、必要な整形・集計を再現可能な処理として実装してください。
元データ、計算過程、表示結果を分離してください。
主要KPI、集計表、棒グラフまたは折れ線グラフを含むサンプルを作成してください。

### management

原則として次のシートを作成してください。

- Readme
- Management
- Master
- Summary

Excelテーブル、フィルター、ウィンドウ枠固定、入力規則、条件付き書式を設定してください。
期限超過、必須項目の未入力、長期間未更新などを識別できるサンプルにしてください。
入力値の選択肢や閾値はMasterシートへ分離してください。

### workflow

原則として次のシートを作成してください。

- Readme
- Process_List
- Roles
- Summary

業務名、担当、頻度、所要時間、前工程、後工程、課題、改善案を管理できるようにしてください。
複雑なフローチャートを図形で描かず、並べ替え・絞り込み可能な表として構造化してください。

## 共通仕様

- タイトル、見出し、入力セル、計算セル、出力セルを視覚的に区別する
- 数値、割合、金額、日付は文字列ではなく適切なデータ型で保存する
- pandas読込時に列ごとの想定型と実際の型を確認し、不一致を黙って補正しない
- 欠損、重複、結合できなかったキーを確認し、件数を記録する
- 入力欄には必要に応じて入力規則を設定する
- 表にはフィルターとウィンドウ枠固定を設定する
- 列幅と行高を内容に合わせて調整する
- 長い文字列は極端に縮小せず、折り返し、列幅調整、別シート化を優先する
- 複雑な数式を1セルに詰め込まず、必要に応じて計算列を分ける
- 数式エラー、参照切れ、必須シート不足をvalidator.pyで検査する
- openpyxlはExcel数式の計算エンジンではないことをREADME.mdに明記する
- 数式を含むブックはExcelで開いた際に再計算される設定にする
- 元データ件数、除外件数、集計前後の合計など、主要な照合結果を記録する

## .github/copilot-instructions.md

このプロジェクトで常に守る短いルールとして、次を記載してください。

- pandasはデータ処理、openpyxlはExcel生成と書式設定を主に担当する
- inputsとtemplatesを上書きしない
- 生成物はoutputsへ保存する
- 数値、日付、割合は適切なデータ型で保持する
- 計算過程を追跡可能にする
- theme、styles、profiles、workbook_specの責務を混在させない
- 三菱電機スタンダードの配色を使用する
- テストはunittestを使用する
- 追加依存を安易に増やさない
- 生成後にvalidatorとunittestを実行する

## 実装手順

### Step 1
現在のファイル構成を確認し、既存ファイルがある場合は役割を整理する。元ファイルは上書きしない。

### Step 2
design/excel_design_spec.mdとworkbook_spec.jsonの初期版を作成する。

### Step 3
theme.py、styles.py、data_pipeline.py、workbook.pyを実装する。

### Step 4
analysis、management、workflowの3つのprofileを実装する。

### Step 5
3種類のサンプルExcelを生成する。

### Step 6
validator.pyとunittestを実装し、検査結果を修正する。

### Step 7
利用可能な環境では生成した各シートを目視確認し、文字切れ、狭すぎる列、見づらいグラフ、色の過剰使用を修正する。目視確認できない場合は、その制約をREADME.mdに記載する。

### Step 8
README.mdと.github/copilot-instructions.mdを完成させる。

## 完了条件

- 3種類のサンプルExcelがエラーなく生成される
- `python -m unittest discover -s tests` が成功する
- validatorの重大エラーが0件である
- 各ファイルで入力、計算、出力の区別が確認できる
- 数値、割合、金額、日付が適切なデータ型と表示形式で保存されている
- 文字切れ、読めないグラフ、過剰な赤背景がない
- pandasによるデータ加工と集計の流れを追跡できる
- workbook_spec.jsonに色、フォント、セル座標が含まれていない
- design/excel_design_spec.mdが存在する
- .github/copilot-instructions.mdが存在する
- README.mdの手順だけで環境構築、生成、検査を再現できる

最初からすべてのExcel用途を扱う巨大な仕組みを作らないでください。初期3種類を基準とし、実際に必要になった用途だけprofileとして追加してください。

最も重要なのは、「Copilotが毎回Excelを自由に装飾する」のではなく、「pandasで再現可能にデータを処理し、決められたテーマ、スタイル、profileを使ってopenpyxlでExcelを生成する」状態を作ることです。

使い方: 初回は空のプロジェクトフォルダで実行できます。基盤の確認後、分析対象をinputs/、見た目の参考をreferences/、継承したいExcelをtemplates/へ置き、workbook_spec.jsonを更新して再生成します。
