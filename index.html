02

各ファイルの役割

1ファイル1責務を基本に、Copilotが変更範囲を判断しやすい境界を作ります。

README.md

セットアップ、実行方法、設計方針、成果物の場所を記載。

requirements.txt

python-pptxを基本とし、明確に必要な依存だけを固定。

.gitignore

仮想環境、キャッシュ、生成した.pptxをGit対象外にする。

.github/copilot-instructions.md

設計の要点をGitHub Copilotへ常時適用する短いルール。

template/

スライドマスター、ロゴ、フッターなど生成時の土台。元ファイルは上書きしない。

references/

参考にするPDFやPPTXを読み取り専用で置き、構造と見た目を分析。

design/reference_analysis.md

参考資料から確認した共通ルール、差異、確認できなかった制約を記録。

design/design_spec.md

設計仕様の正本。変更時は先に更新し、theme.pyとテストを同期。

tools/analyze_references.py

参考PPTXの色、フォントサイズ、座標、図形サイズを機械分析。

inputs/slides.json

文章、数値、画像パス、layout_idなど内容だけを記述。生成処理からは変更しない。

pptxgen/theme.py

色、書体、文字サイズ、間隔、semantic styleを一元管理。

pptxgen/components.py

指定領域へ統一された部品を描画し、低レベルAPIを隠蔽。

pptxgen/layouts/

座標と領域配置、layout固有の情報量上限を管理。

tests/test_generation.py

標準のunittestで生成、layout解決、validator結果を確認。

outputs/

生成したPowerPointを新しいファイルとして保存する場所。.gitkeepのみ管理対象。

04

Copilotに渡す初期構築プロンプト

Agent modeで、参考資料・三菱電機のVisual Identity・DADS v2.17.1の設計原則を統合し、再利用可能なPowerPoint生成基盤を構築する実践版です。

copilot-foundation-prompt.txt
あなたは、python-pptxを使って高品質なPowerPoint資料を自動生成するための「PowerPoint生成基盤」を、現在のworkspace内に実際に構築するエンジニアです。

このプロンプトはGitHub CopilotのAgent mode、または同等に複数ファイルの作成・編集とターミナル実行が可能な自律実行環境で使うことを前提とします。
説明やコード例を回答するだけで終了せず、workspace内のファイルを作成・編集し、サンプルPowerPointの生成、検証、テスト、ドキュメント整備まで完了条件を満たすところまで進めてください。

目的は、Copilotが毎回スライドを自由描画するのではなく、決められたデザインシステム、再利用可能なcomponents、layout library、入力契約を使ってPowerPointを生成する状態を作ることです。

特に次の問題を構造的に防いでください。

- 背景色と文字色が同化する
- スライドごとにフォント、文字サイズ、余白がばらつく
- 図形の位置やサイズが不揃いになる
- テキストがはみ出す
- 1枚の情報量が過多になる
- 色、座標、書体がコード各所に分散する
- 同じ部品がlayoutごとに再実装される
- slides.jsonの構造がlayoutごとに場当たり的になる
- 「コンサル資料らしい」情報階層や視線誘導にならない

# 1. 実行前確認と進め方

最初に現在のworkspaceを確認してください。

確認対象：
- Pythonの利用可否
- python-pptxの利用可否
- template/
- references/
- inputs/
- 既存のpptxgen/、design/、tests/、README.md
- 既存ファイルを上書きすると影響があるか

既存実装がある場合は、全面破棄せず、今回のarchitectureへ安全に統合してください。

技術的に実行不能、または結果を大きく左右する重大な情報欠落がある場合だけ停止してください。
それ以外の軽微な不足や差異は、後述の優先順位に従って妥当な判断で進め、判断理由をdesign/design_spec.mdへ記録してください。

template/、references/、inputs/は読み取り専用として扱い、上書き、編集、移動、削除をしないでください。
生成物はoutputs/へ新しいファイル名で保存し、既存生成物も明示的な指示なく上書きしないでください。

# 2. 設計判断の優先順位

デザインや実装方針が競合する場合は、次の順に優先してください。

1. このプロンプトおよびユーザーが明示した要件
2. template/に含まれるブランド必須要素
3. 三菱電機公式referencesに共通して確認できるVisual Identity
4. デジタル庁デザインシステム（DADS）v2.17.1から採用するDesign System原則
5. コンサルティング資料としての一般的な情報設計原則

この順位で解決できる差異については確認を求めず進めてください。
templateとreferencesの差異、採用した判断、確認できなかった事項はdesign/reference_analysis.mdまたはdesign/design_spec.mdへ記録してください。

# 3. Architecture

PowerPoint生成基盤を次の責務に分離してください。

## theme.py
デザイン値の正本です。

管理対象：
- Primitive Color Token
- Semantic Color Token
- Surface Style
- Typography Token
- Spacing Token
- Border Token
- Corner Token
- slide margin
- grid gutter
- 最小フォントサイズ
- validatorで共有するデザイン基準値

スライド固有の絶対座標は持たせないでください。

## geometry.py
座標計算だけを担当します。

最低限：
- Box
- SlideGrid
- content_area()
- 12-column logical grid
- column spanからBoxを計算する処理

色、フォント、spacing値そのものをgeometry.pyへ重複定義しないでください。
marginやgutterの値はtheme.pyを参照してください。

## components.py
再利用可能な描画部品を担当します。

- layoutからBoxまたはx/y/w/hを受け取る
- themeを参照して描画する
- python-pptxの低レベルAPIを隠蔽する
- スライド全体の領域分割を判断しない

## layouts/
1枚のスライド全体の情報配置を担当します。

- geometryのGridとBoxを利用する
- componentsを組み合わせる
- layout固有の最大文字量、最大項目数、必須項目を管理する
- rawな色コード、フォント名、フォントサイズを持たない
- slides.jsonから座標を受け取らない

## renderer.py
入力とlayout実装の橋渡しを担当します。

- slides.jsonを読み込む
- layout_idを解決する
- LAYOUT_REGISTRYから対応layoutを呼ぶ
- layoutごとのdata contractを検証してから描画する
- 未知のlayout_idを拒否する

## slides.json
内容だけを持つ入力です。

許可：
- layout_id
- title
- message
- heading
- body
- bullets
- KPI
- chart data
- image path
- source
- layoutが定義した内容項目

禁止：
- x
- y
- width
- height
- font_size
- font_name
- text_color
- fill_color
- line_color
- その他の直接的なデザイン指定

# 5. 技術・依存関係

- Pythonを使用する
- PowerPoint生成にはpython-pptxを使用する
- テストにはPython標準ライブラリのunittestを使用する
- pytestは導入しない
- python-pptx以外の追加依存は、標準ライブラリでは実現できない明確な必要性がある場合だけ追加する
- PyYAMLやPillowを初期前提として追加しない
- 入力形式は標準ライブラリで扱えるJSONを基本とする
- テストは python -m unittest discover -s tests で実行できるようにする
- PowerPoint上で後から個別編集できる状態を維持する
- スライドを画像化して貼り付ける方式にしない
- 入力資料や生成物を外部サービスへ送信しない

追加依存が必要になった場合は、理由と標準ライブラリで代替できない理由をREADME.mdへ記録してください。

# 6. デザイン設計の3層構造

デザインを次の3層として扱ってください。

## A. Visual Identity：三菱電機
担当：
- ブランドカラー
- ロゴ
- 企業資料としてのトーン
- templateのブランド必須要素
- 三菱電機公式referencesから確認できる視覚的特徴

基本は「白ベース＋ブランドレッド＋チャコール／グレー」です。

## B. Design System：DADS v2.17.1を参考
担当：
- Design Token
- Typography hierarchy
- modular spacing
- logical grid
- semantic color
- reusable component
- accessibility
- consistency

DADSのWeb UIをPowerPointへコピーすることが目的ではありません。
DADS固有の青系Visual Identityへ変更しないでください。

採用しないWeb固有要素：
- breakpoint
- responsive / liquid layout
- hover / focus / active
- DOM / HTML構造
- Webフォーム
- Webナビゲーション
- Web UIコンポーネントそのもの
- リフロー要件

## C. Information Design：コンサルティング資料
担当：
- 1スライド1メッセージ
- タイトル
- ページメッセージ
- メッセージを裏付ける図、表、数値、情報
- 情報階層
- 視線誘導
- 比較のしやすさ
- 図解
- KPI
- Before / After
- Process
- Matrix
- Chart + Insight

装飾よりも情報伝達を優先してください。
情報量超過時はフォント縮小よりスライド分割を優先してください。

# 7. Design Token

theme.pyでTokenを一元管理してください。

## Primitive Color
例：
- BRAND_RED
- GRAY_900
- GRAY_700
- GRAY_500
- GRAY_300
- GRAY_100
- WHITE

三菱電機の正式なtemplateまたはreferencesからより適切な値を確認できた場合は、そちらを優先してdesign_spec.mdへ記録してください。

基準値として以下を利用できます。

- BRAND_RED: #E60012
- PRIMARY_TEXT相当: #1A1A1A
- SECONDARY_TEXT相当: #555555
- DARK_GRAY: #333333
- MID_GRAY: #6E6E6E
- BORDER_GRAY: #D9D9D9
- LIGHT_GRAY: #F2F2F2
- VERY_LIGHT_GRAY: #F7F7F7
- BACKGROUND: #FFFFFF

## Semantic Color
実際に使うものだけ定義してください。

例：
- TEXT_PRIMARY
- TEXT_SECONDARY
- BORDER_DEFAULT
- BACKGROUND
- ACCENT
- POSITIVE
- CAUTION
- NEGATIVE
- DISABLED

ブランドレッドは主にACCENTとして扱ってください。
警告やエラーとブランド色が混同される場合は、色だけに依存せずラベル、記号、形状、位置を併用してください。

## Surface Style
背景色と文字色を安全な組み合わせとして定義してください。

最低限：
- WHITE_PANEL
- LIGHT_PANEL
- RED_ACCENT_PANEL
- DARK_PANEL

例：
- WHITE_PANEL：white background + dark text + light border
- LIGHT_PANEL：light gray background + dark text + light border
- RED_ACCENT_PANEL：brand red background + white text
- DARK_PANEL：dark gray background + white text

component側はstyle=WHITE_PANELのように利用し、背景色と文字色を別々に自由指定しない設計を基本としてください。

## Typography
用途ベースで少数のTokenを定義してください。

- TITLE
- MESSAGE
- HEADING
- BODY
- CAPTION
- NOTE
- KPI_VALUE

フォントウェイトはRegularとBoldを中心にしてください。
DADSのNoto Sans JP自体を必須にしません。
template、references、実行環境で利用可能なフォントを優先し、日本語フォールバック候補をtheme.pyへ定義してください。

フォントサイズはtemplateとreferencesの分析結果を優先し、スライドごとに自由なサイズを作らないでください。

## Spacing
3〜5段階程度のモジュラースケールを定義してください。

例：
- SPACE_XS
- SPACE_SM
- SPACE_MD
- SPACE_LG
- SPACE_XL

DADSの8 CSS pxという値をPowerPointへ直接コピーしないでください。
PowerPointの16:9固定キャンバス、文字サイズ、template、referencesをもとに適切な値へ変換してください。

同じ意味の要素には同じspacingを適用してください。
関連が強い要素ほど近く、異なる情報グループほど大きく離してください。

# 8. Grid / Geometry

DADSの12カラムグリッドを「主要領域の論理Grid」として参考にしてください。

代表的な領域分割：
- 12
- 9 + 3
- 8 + 4
- 6 + 6
- 4 + 8
- 3 + 9
- 4 + 4 + 4
- 3 + 6 + 3

SlideGridはmarginとgutterをtheme.pyから受け取り、column spanからBoxを返せるようにしてください。

例となる意図：
- main = grid.span(1, 8)
- side = grid.span(9, 4)

ただし、全shapeを12カラムへ強制的にsnapさせないでください。
Gridが拘束するのは主にスライドの主要領域です。
card内部のpadding、アイコン、矢印、装飾、component内部の細かな配置は、受け取ったBox内で相対配置して構いません。

geometry.pyを巨大なlayout engineにしないでください。

# 9. templateとreferences

## template
template/consulting_template.pptxが存在する場合は生成の土台として利用してください。

可能な範囲で継承：
- slide size
- master
- existing layout
- logo
- footer
- font
- ブランド必須要素

templateが存在しない場合は白紙の16:9プレゼンテーションから生成してください。

## references
references/は分析用の見本です。生成ベースとして直接利用しません。

三菱電機公式資料を3〜6資料程度用意することを推奨します。
資料数より、要約、比較、プロセス、グラフなど異なる表現を代表できることを優先してください。

PDFの全ページを機械的に処理する必要はありません。
視覚分析は代表性の高いページを中心に、合計10〜20ページ程度を目安にしてください。

PDFを視覚入力として確認できる環境では、見た目、情報密度、視線誘導、余白、カード、表、グラフを分析してください。

PDFを視覚的に確認できない場合：
- 確認したと仮定しない
- テキスト抽出だけから色、余白、レイアウトを断定しない
- PPTXなど機械分析可能な資料があれば補完に使う
- 制約をreference_analysis.mdへ記録する
- templateと利用可能なreferences、既定のVisual Identity、DADS原則を使って構築自体は続行する

PPTXがある場合はtools/analyze_references.pyを使い、python-pptxで色、フォントサイズ、座標、図形サイズなどを機械分析してください。

参考資料の本文、図、写真、ロゴを転載せず、抽象化したデザインルールとlayout patternだけを利用してください。

# 10. reference_analysis.md

実装前に、確認できたreferencesから次を整理してください。

- slide size / aspect ratio
- background
- color
- typography
- margins
- spacing
- line
- corner
- card / box
- emphasis
- logo / footer
- information density
- recurring layout pattern
- recurring component
- グラフ表現
- 視覚確認できなかった制約

単一スライドの値をそのまま標準化せず、複数資料から共通性を抽出してください。

reference_analysis.mdは「実物から何を観察したか」の記録です。

# 11. 初期layout library

原則として次の7種類を実装してください。

1. executive_summary
   - 結論、重要論点、経営層向け要約

2. two_column
   - 2テーマ比較
   - 課題と対応
   - 文章と図の並置

# 15. Color / 三菱電機スタンダード

資料全体は「白ベース＋ブランドレッド＋チャコール／グレー」を基本としてください。

- 背景は原則白
- 白地を十分に残す
- ブランドレッドは重要箇所に限定
- 通常本文はdark gray / charcoal
- 補助領域はlight gray
- 赤を大面積背景として多用しない
- 赤だけで意味を区別しない
- 通常系列はgray、注目系列はbrand redを基本とする
- 技術資料、業務改善資料、DX資料に使えるフォーマルで信頼感のある印象を目指す

DADSのカラーへ置き換えないでください。

# 16. Accessibility

アクセシビリティをデザイン品質の一部として扱ってください。

基本方針：
- 文字と背景のコントラスト比は原則4.5:1以上を目安
- 重要な非テキスト要素は3:1以上を目安
- 色だけで意味を伝えない
- 極端に小さい文字で情報量超過を解決しない
- テキストoverflowを検出する
- 情報密度が高すぎる場合は分割を優先する

写真、gradient、透過shapeなど機械判定が難しいケースを無理にERROR判定しないでください。
確実に判定できるSemantic Styleを中心に自動検証し、判定が不確かなものはWARNINGまたは目視確認対象としてください。

# 17. validator.py

validatorはERRORとWARNINGを分けてください。

## ERRORの例
- slide外へのはみ出し
- 未知のlayout_id
- 必須項目不足
- slides.jsonに禁止design fieldがある
- 最小フォントサイズ違反
- 定義外colorの明らかな使用
- 確実に判定可能な背景と文字のcontrast不足
- 生成PPTXを再度開けない

## WARNINGの例
- titleが長い
- body量が多い
- 情報密度が高い
- object overlapの可能性
- contrastを機械判定できない
- layout上限に近い

意図的な重なり：
- 親containerと内部要素
- background shape
- arrow
- decoration
などを可能な範囲で除外してください。

WARNINGが残っているだけで生成失敗にしないでください。
完了条件はERROR=0です。

validatorを完璧なPowerPoint layout engineにしないでください。
まず生成品質を優先してください。

# 18. Text Overflow

## 技術方針

- Python 3を使用する

- 元の入力ファイル、参考資料、テンプレートを上書きしない
- 実データがないサンプルでは、架空データであることを明記する
- 実際の業務用ファイルでは、与えられていない数値や事実を作らない

## カラーテーマ：三菱電機スタンダード

PowerPoint生成基盤と同じ「白ベース＋ブランドレッド＋チャコール／グレー」にしてください。

theme.pyで次の色を一元管理してください。

- BRAND_RED: #E60012
- PRIMARY_TEXT: #1A1A1A
- SECONDARY_TEXT: #555555
- DARK_GRAY: #333333
- MID_GRAY: #6E6E6E
- BORDER_GRAY: #D9D9D9
- LIGHT_GRAY: #F2F2F2
- VERY_LIGHT_GRAY: #F7F7F7
- BACKGROUND: #FFFFFF

基本ルールは次のとおりです。

- シート背景と通常セルは白を基本とする
- ブランドレッドは重要KPI、警告、注目系列、重要見出しに限定する
- 通常の見出しと本文にはチャコールまたはダークグレーを使用する
- 補助領域、入力説明、集計カードにはライトグレーを使用する
- 赤を表全体や大面積の背景に使用しない
- 赤だけで状態を区別せず、文字、記号、位置、ラベルを併用する
- 派手な装飾より、入力しやすさ、読みやすさ、比較しやすさを優先する
- 日本語フォントはYu Gothicを第一候補とする
- templateに指定フォントや正式なブランドカラーがある場合はtemplateを優先し、採用値をdesign/excel_design_spec.mdへ記録する

色、フォント、書式、配置の責務を次のように分離してください。

- theme.py：色、フォント、数値・割合・金額・日付の表示形式
- styles.py：themeの値を使ってセル、表、見出し、KPI、グラフへ書式を適用
- profiles/：シート構成、列構成、各領域の配置
- workbook_spec.json：タイトル、項目、数値、入力ファイル、生成タイプ

workbook_spec.jsonに色コード、フォント名、セル座標を持たせないでください。

## 3種類の生成profile

### analysis

原則として次のシートを作成してください。

- Readme
- Raw_Data
- Calculation
- Summary
- Dashboard

pandasを使って元データの型、欠損、重複を確認し、必要な整形・集計を再現可能な処理として実装してください。
元データ、計算過程、表示結果を分離してください。
主要KPI、集計表、棒グラフまたは折れ線グラフを含むサンプルを作成してください。

### management

原則として次のシートを作成してください。

- Readme
- Management
- Master
- Summary

Excelテーブル、フィルター、ウィンドウ枠固定、入力規則、条件付き書式を設定してください。
期限超過、必須項目の未入力、長期間未更新などを識別できるサンプルにしてください。
入力値の選択肢や閾値はMasterシートへ分離してください。

### workflow

原則として次のシートを作成してください。

- Readme
- Process_List
- Roles
- Summary

業務名、担当、頻度、所要時間、前工程、後工程、課題、改善案を管理できるようにしてください。
複雑なフローチャートを図形で描かず、並べ替え・絞り込み可能な表として構造化してください。

## 共通仕様

- タイトル、見出し、入力セル、計算セル、出力セルを視覚的に区別する
- 数値、割合、金額、日付は文字列ではなく適切なデータ型で保存する
- pandas読込時に列ごとの想定型と実際の型を確認し、不一致を黙って補正しない
- 欠損、重複、結合できなかったキーを確認し、件数を記録する
- 入力欄には必要に応じて入力規則を設定する
- 表にはフィルターとウィンドウ枠固定を設定する
- 列幅と行高を内容に合わせて調整する
- 長い文字列は極端に縮小せず、折り返し、列幅調整、別シート化を優先する
- 複雑な数式を1セルに詰め込まず、必要に応じて計算列を分ける
- 数式エラー、参照切れ、必須シート不足をvalidator.pyで検査する
- openpyxlはExcel数式の計算エンジンではないことをREADME.mdに明記する
- 数式を含むブックはExcelで開いた際に再計算される設定にする
- 元データ件数、除外件数、集計前後の合計など、主要な照合結果を記録する

## .github/copilot-instructions.md

このプロジェクトで常に守る短いルールとして、次を記載してください。

- pandasはデータ処理、openpyxlはExcel生成と書式設定を主に担当する
- inputsとtemplatesを上書きしない
- 生成物はoutputsへ保存する
- 数値、日付、割合は適切なデータ型で保持する
- 計算過程を追跡可能にする
- theme、styles、profiles、workbook_specの責務を混在させない
- 三菱電機スタンダードの配色を使用する
- テストはunittestを使用する
- 追加依存を安易に増やさない
- 生成後にvalidatorとunittestを実行する

## サンプルとテスト

小規模な架空データを使って、次の3ファイルを生成してください。

- outputs/sample_analysis.xlsx
- outputs/sample_management.xlsx
- outputs/sample_workflow.xlsx

unittestで次を検査してください。

- 3種類のサンプルExcelが生成される
- 各profileの必須シートと必須列が存在する
- Excelテーブルとフィルターが設定されている
- ウィンドウ枠固定が設定されている
- 必要な入力規則と条件付き書式が設定されている
- 指定したテーマカラーが使用されている
- 数式に明らかな参照エラーがない
- 入力ファイルとtemplateが上書きされていない
- pandasによる集計前後の件数または合計が照合できる

`python -m unittest discover -s tests` を実行し、失敗を修正してください。

## 実装手順

### Step 1
現在のファイル構成を確認し、既存ファイルがある場合は役割を整理する。元ファイルは上書きしない。

### Step 2
design/excel_design_spec.mdとworkbook_spec.jsonの初期版を作成する。

### Step 3
theme.py、styles.py、data_pipeline.py、workbook.pyを実装する。

### Step 4
analysis、management、workflowの3つのprofileを実装する。

### Step 5
3種類のサンプルExcelを生成する。

### Step 6
validator.pyとunittestを実装し、検査結果を修正する。

### Step 7
利用可能な環境では生成した各シートを目視確認し、文字切れ、狭すぎる列、見づらいグラフ、色の過剰使用を修正する。目視確認できない場合は、その制約をREADME.mdに記載する。

### Step 8
README.mdと.github/copilot-instructions.mdを完成させる。

## 完了条件

- 3種類のサンプルExcelがエラーなく生成される
- `python -m unittest discover -s tests` が成功する
- validatorの重大エラーが0件である
- 各ファイルで入力、計算、出力の区別が確認できる
- 数値、割合、金額、日付が適切なデータ型と表示形式で保存されている
- 文字切れ、読めないグラフ、過剰な赤背景がない
- pandasによるデータ加工と集計の流れを追跡できる
- workbook_spec.jsonに色、フォント、セル座標が含まれていない
- design/excel_design_spec.mdが存在する
- .github/copilot-instructions.mdが存在する
- README.mdの手順だけで環境構築、生成、検査を再現できる

最初からすべてのExcel用途を扱う巨大な仕組みを作らないでください。初期3種類を基準とし、実際に必要になった用途だけprofileとして追加してください。

最も重要なのは、「Copilotが毎回Excelを自由に装飾する」のではなく、「pandasで再現可能にデータを処理し、決められたテーマ、スタイル、profileを使ってopenpyxlでExcelを生成する」状態を作ることです。

使い方: 初回は空のプロジェクトフォルダで実行できます。基盤の確認後、分析対象をinputs/、見た目の参考をreferences/、継承したいExcelをtemplates/へ置き、workbook_spec.jsonを更新して再生成します。
